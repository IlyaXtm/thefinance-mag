## اگر فقط بخش مجله را تحویل می‌گیری

پیش‌تر یک سند جدا برای این وجود داشت. **جدا نگه داشته نشد** — دو سند که ۸۰٪
مشترک دارند ظرف یک ماه با هم اختلاف پیدا می‌کنند، و آن‌وقت معلوم نیست کدام درست
است. به‌جایش، این‌ها بخش‌هایی هستند که به مجله مربوط‌اند:

| بخش | چرا برای مجله لازم است |
|---|---|
| ۲ — TLS روی سرور نیست | تله‌ی hairpin از همین می‌آید |
| ۳ — کانفیگ nginx | دو بلاک به کانتینر مجله، چهار بلاک به CMS |
| ۴ — درسی که یک بار سایت را شکست | `grep` قبل از خاموش کردن هر کانتینری |
| ۵ — کانتینر مجله و متغیرهایش | دقیقاً چه چیزی باید اجرا شود |
| ۶ — روی سرور پروداکشن بیلد نکن | یک بیلد اینجا `/inchart` را خواباند |
| ۹ — تأیید بعد از انتقال | شامل چک هر ۵۴ مقاله |

و **تله‌ی hairpin**، که ارزش دارد قبل از هر کاری خوانده شود، چون یک بار همه‌ی
تصاویر را خواباند:

nginx روی این سرور فقط پورت ۸۰ دارد و TLS در CDN تمام می‌شود. پس اگر کدی روی
سرور بخواهد `https://thefinance.ir/...` را fetch کند، درخواست از سرور بیرون
می‌رود، به CDN می‌رسد و **به همان سرور برمی‌گردد** — و تایم‌اوت می‌شود.

برای همین بهینه‌ساز تصاویر Next از `wp.thefinance.ir` می‌خواند، نه از دامنه‌ی
عمومی. **این در کد ثبت شده است؛ دست نزن.**

## ۱ — چه چیزی روی این سرور اجرا می‌شود

**بیشتر از چیزی است که در نگاه اول به‌نظر می‌رسد.** این فهرست با بازرسی واقعی سرور به‌دست آمده، نه از حافظه.

### کانتینرها

| چه چیزی | پورت | کانتینر | وضعیت |
|---|---|---|---|
| سایت اصلی | ۷۹۰۲ | `thefinance-front` | فعال |
| مجله (Next.js) | ۳۱۰۰ | `thefinance-mag` | فعال |
| **پارادایم** | — | `thefinance-paradigm-front` | فعال، دو ماه |
| نسخه‌ی قبلی مجله | — | `thefinance-mag-prev` | متوقف، برای rollback |

**پارادایم روی همین سرور است.** یک محصول کامل و جدا. اگر در انتقال جا بماند، می‌خوابد.

و الگوی برچسب‌گذاری‌اش تمیزتر از مجله است — `current` به‌علاوه‌ی `rollback-1` تا `rollback-4`. در انتقال، همه‌ی این ایمیج‌ها لازم‌اند، نه فقط `current`.

### سرویس‌های روی خود هاست

| چه چیزی | کجا |
|---|---|
| nginx | `/etc/nginx/conf.d/thefinance.ir.conf` |
| **GitLab Runner** | `/etc/gitlab-runner/config.toml` |

### 🔴 GitLab Runner — دیپلوی سایت اصلی خودکار است

```
gitlab-runner.service   active running   از ۱۲ جولای
```

دو ماه است اجرا می‌شود و همین هفته بیلد اجرا کرده.

**اگر منتقل نشود، دیپلوی خودکار سایت اصلی می‌شکند** — و ممکن است هفته‌ها طول بکشد تا کسی متوجه شود، چون تا وقتی کسی push نکند خطایی دیده نمی‌شود.

کانفیگش را ببر:

```bash
sudo cat /etc/gitlab-runner/config.toml
```

و بعد از انتقال، runner روی سرور جدید باید **دوباره ثبت شود** — نه فقط کانفیگ کپی شود، چون توکن ثبت به ماشین گره خورده.

### 🔴 کاربر `deploy` و کلیدش

```
/home/deploy/.ssh/
  authorized_keys   ← کلید خودش
  id_rsa            ← کلید خصوصی
```

از تاریخچه‌ی شلش معلوم است چه شده: کلید ساخته شده، **کلید خصوصی به base64 تبدیل شده تا در متغیر GitLab CI گذاشته شود**.

یعنی کلید خصوصی این سرور احتمالاً در متغیرهای CI ذخیره است. و این کاربر به داکر دسترسی دارد، که عملاً root است.

**در انتقال، کلید را کپی نکن.** روی سرور جدید جفت کلید تازه بساز، در GitLab جایگزین کن، و کلید قدیمی را باطل کن. کپی کردن یعنی یک کلید که شش ماه است در CI نشسته، شش ماه دیگر هم می‌ماند.

**و این کاربر را حذف نکن** تا مسیر دیپلوی جدید کار کند — سایت اصلی به آن وابسته است.

## ۲ — 🔴 مهم‌ترین نکته: TLS روی این سرور نیست

**nginx فقط روی پورت ۸۰ گوش می‌دهد.** هیچ گواهی SSL روی این سرور نیست و لازم هم نیست.

TLS در **CDN ستون** پایان می‌یابد. CDN درخواست HTTPS کاربر را می‌گیرد، رمزگشایی می‌کند، و به‌صورت HTTP به این سرور می‌فرستد.

### چرا این مهم است

اگر روی سرور جدید Let's Encrypt یا هر گواهی دیگری راه بیندازی و nginx را روی ۴۴۳ ببری، **CDN نمی‌تواند وصل شود** مگر تنظیماتش هم عوض شود.

و مهم‌تر: این معماری یک تله دارد که یک بار سایت را خواباند. اگر کدی روی سرور بخواهد `https://thefinance.ir/...` را fetch کند، درخواست از سرور بیرون می‌رود، به CDN می‌رسد، و برمی‌گردد به همان سرور — **hairpin** — و تایم‌اوت می‌شود.

برای همین، بهینه‌ساز تصاویر Next از `wp.thefinance.ir` می‌خواند نه از دامنه‌ی عمومی. آن در کد ثبت شده؛ دست نزن.

## ۳ — 🔴 کانفیگ nginx مهم‌ترین دارایی این سرور است

فایل: `/etc/nginx/conf.d/thefinance.ir.conf`

**این فایل را کپی کن، از نو ننویس.** حدود دوازده بلاک `location` دارد و هر کدام یک مشکل مشخص را حل می‌کند که با آزمون و خطا پیدا شده.

نسخه‌ی مرجعش در مخزن هم هست: `infra/nginx/thefinance.ir.conf` در ریپوی `IlyaXtm/thefinance-mag`.

### بلاک‌ها به ترتیب اهمیت

```nginx
location / { proxy_pass http://127.0.0.1:7902; }     # سایت اصلی
location /mag/ { proxy_pass http://127.0.0.1:3100; } # مجله
location ^~ /mag/_next { proxy_pass http://127.0.0.1:3100; }
```

و چهار بلاک که به **سرور CMS** می‌روند، نه به این سرور:

```nginx
location /mag/wp-content/uploads/  → https://wp.thefinance.ir/wp-content/uploads/
location ^~ /mag/wp-includes/      → https://wp.thefinance.ir/wp-includes/
location ^~ /mag/wp-content/plugins/ → https://wp.thefinance.ir/wp-content/plugins/
location ^~ /mag/wp-content/themes/  → https://wp.thefinance.ir/wp-content/themes/
```

**این چهار تا حیاتی‌اند.** اگر منتقل نشوند: تصاویر مجله همه ۵۰۲ می‌دهند و پنل ادمین وردپرس بدون CSS می‌آید.

هر کدام `proxy_ssl_server_name on;` دارد — چون به یک هاست HTTPS با SNI می‌روند.

### و بلاک‌های مسیریابی زبان

```nginx
location ~ ^/(fa|en|ar)$      { ... }
location ~ ^/(fa|en|ar)/(.*)$ { ... }
```

مال سایت اصلی است. دست نزن.

## ۴ — 🔴 درسی که یک بار سایت را شکست

روزی که وردپرس جنه را خاموش کردیم، **همه‌ی تصاویر سایت رفتند** — چون بلاک `uploads` به پورت ۹۰۸۰ می‌رفت.

و تا وقتی کش CDN تازه نشد، هیچ‌کس نفهمید.

**قبل از خاموش کردن، حذف کردن یا تغییر هر سرویسی:**

```bash
sudo grep -rn "<پورت یا نام>" /etc/nginx/
```

سه ثانیه کار است و یک قطعی را می‌گیرد.

الان هیچ بلاکی به ۹۰۸۰ اشاره نمی‌کند و جنه حذف شده. ولی قاعده می‌ماند: **در انتقال، قبل از خاموش کردن هر کانتینری روی سرور قدیمی، `grep` بزن.**

## ۵ — کانتینر مجله و متغیرهایش

```bash
sudo docker run -d --name thefinance-mag --restart unless-stopped \
  -p 127.0.0.1:3100:3000 \
  -e WP_PREVIEW_SECRET=<از CMS بگیر> \
  -e WP_GRAPHQL_ENDPOINT=https://wp.thefinance.ir/mag/graphql \
  -e NEXT_PUBLIC_USE_MOCK=false \
  -e NEXT_PUBLIC_WP_GRAPHQL_ENDPOINT=https://wp.thefinance.ir/mag/graphql \
  -e NEXT_PUBLIC_SITE_ORIGIN=https://thefinance.ir \
  -e NODE_ENV=production -e NEXT_TELEMETRY_DISABLED=1 -e PORT=3000 \
  thefinance-mag:ef44f99
```

### نکته‌های مهم

**`-p 127.0.0.1:3100:3000`** — کانتینر فقط روی لوکال‌هاست گوش می‌دهد. اگر `0.0.0.0` بگذاری، پورت ۳۱۰۰ از اینترنت قابل دسترس می‌شود و مجله بدون CDN و بدون nginx سرو می‌شود.

**`WP_PREVIEW_SECRET`** باید **دقیقاً** با مقدار روی CMS یکی باشد، وگرنه پیش‌نمایش پیش‌نویس کار نمی‌کند:

```bash
# روی سرور CMS
sudo docker exec wp-wordpress-1 grep "TF_MAG_PREVIEW_SECRET" /var/www/html/wp-config.php | grep -o "[a-f0-9]\{64\}"
```

**این مقدار را در چت یا پیام نفرست.** دو بار در این پروژه لو رفت و دو بار چرخانده شد. برای مقایسه‌ی دو مقدار، هشت کاراکتر اول کافی است.

**`NEXT_PUBLIC_*`** در زمان بیلد جا می‌افتند، نه در زمان اجرا. اگر لازم شد عوض شوند، بیلد جدید لازم است.

## ۶ — 🔴 روی سرور پروداکشن بیلد نکن

یک `docker build` روی این سرور، `/inchart` را از پا انداخت — چون چهار سرویس روی یک ماشین‌اند و بیلد Next تمام CPU را می‌گیرد.

**روش درست:** بیلد روی مک، انتقال ایمیج:

```bash
# روی مک
docker build --platform linux/amd64 \
  --build-arg BUILD_ID=$(git rev-parse --short HEAD) \
  --build-arg SITE_ORIGIN=https://thefinance.ir \
  --build-arg WP_GRAPHQL_ENDPOINT=https://wp.thefinance.ir/mag/graphql \
  --build-arg USE_MOCK=false \
  -t thefinance-mag:$SHA .

docker save thefinance-mag:$SHA | gzip > /tmp/mag-$SHA.tar.gz
rsync -avP -e "ssh -i <key>" /tmp/mag-$SHA.tar.gz user@<server>:~/
```

```bash
# روی سرور
gunzip -c ~/mag-$SHA.tar.gz | sudo docker load
```

`--platform linux/amd64` حیاتی است اگر از مک ARM بیلد می‌گیری.

## ۷ — ترتیب انتقال، بدون قطعی

این ترتیب مهم است. اگر IP مبدأ CDN را قبل از آماده بودن سرور جدید عوض کنی، سایت می‌خوابد.

### گام ۱ — سرور جدید را کامل آماده کن

- Docker نصب
- nginx نصب
- کانفیگ nginx کپی شود (از سرور فعلی یا از مخزن)
- ایمیج‌های داکر منتقل شوند
- کانتینرها بالا بیایند
- **ولی هیچ ترافیکی به آن نرود**

### گام ۲ — روی سرور جدید، با IP مستقیم تست کن

```bash
curl -s -o /dev/null -w 'mag %{http_code}\n' -H "Host: thefinance.ir" http://<IP-جدید>/mag/
curl -s -o /dev/null -w 'main %{http_code}\n' -H "Host: thefinance.ir" http://<IP-جدید>/
curl -s http://127.0.0.1:3100/mag/health | python3 -m json.tool
```

آن `-H "Host:"` لازم است چون nginx بر اساس `server_name` مسیریابی می‌کند.

**همه باید ۲۰۰ بدهند قبل از اینکه به گام بعد بروی.**

### گام ۳ — CDN را به IP جدید ببر

در پنل ستون، مبدأ (origin) را عوض کن.

**و بلافاصله تست کن:**

```bash
for u in "/" "/mag/" "/mag/archive" "/inchart" "/mag/wp-content/uploads/2026/09/wti-price-breaks-86-100-day-sma-1.jpg"; do
  printf "%-60s %s\n" "$u" "$(curl -s -o /dev/null -w '%{http_code}' -L "https://thefinance.ir$u?cb=$(date +%s%N)")"
done
```

آن `?cb=` کش را دور می‌زند تا واقعیت مبدأ را ببینی.

### گام ۴ — سرور قدیمی را چند روز نگه دار

نه خاموش، نه حذف. اگر چیزی بیرون زد، برگرداندن مبدأ CDN چند دقیقه است.


**و اگر کانفیگ تغییری کرد، در مخزن هم ثبت شود:**

`infra/nginx/thefinance.ir.conf` در `IlyaXtm/thefinance-mag`.

یک بار کشف شد که کانفیگ سرور از مخزن عقب است و ریت‌لیمیت گراف‌کیوال ماه‌ها اعمال نمی‌شد. **جهت همگام‌سازی همیشه مخزن ← سرور است**، و قبل از هر کامیت از سرور، `git diff` را برای حذف‌ها بخوان.

---

## ۱۲ — سؤالاتی که قبل از شروع باید جواب بگیری

**پارادایم چه ولیوم و متغیری دارد؟** روی همین سرور است و من نمی‌شناسمش.

**سایت اصلی چه؟** همان.

**GitLab Runner را چطور منتقل می‌کنی؟** توکن ثبت به ماشین گره خورده، پس روی سرور جدید باید دوباره ثبت شود نه فقط کانفیگ کپی.

**آیا CMS قاعده‌ای بر اساس IP سرور فرانت دارد؟**

**کرون یا اسکریپت زمان‌بندی‌شده‌ای هست؟**

**سرور جدید چند هسته دارد؟** سه سرویس روی یک ماشین است و یکی‌شان بیلد می‌گیرد.

---

## ۱۳ — چه چیزی را در انتقال بهتر کنیم

انتقال سرور بهترین فرصت برای رفع چند بدهی است، چون به‌هرحال همه‌چیز از نو راه‌اندازی می‌شود:

**کلید `deploy` تازه شود.** کلید فعلی شش ماه است در متغیرهای GitLab CI نشسته. سرور جدید = کلید جدید.

**ایمیج‌های قدیمی منتقل نشوند.** روی سرور فعلی ده ایمیج مجله و پنج ایمیج پارادایم هست. فقط نسخه‌ی فعلی و یکی برای rollback لازم است.

**و بیلد مجله به CI برود.** الان دستی روی مک بیلد می‌شود و با `rsync` منتقل. ورک‌فلو GitHub Actions نوشته شده ولی پوش نشده — و با runner که از قبل روی سرور هست، شاید مسیر ساده‌تری باشد.
