# معماری فرانت‌اند مجله — راهنمای یادگیری

این سند توضیح می‌دهد فرانت‌اند مجله چطور ساخته شده و **چرا** هر تصمیم گرفته شده. هدفش این است که کسی که کد را باز می‌کند، بفهمد نه فقط چه چیزی هست، بلکه چه مسئله‌ای را حل می‌کند.

مثال‌ها از کد واقعی این پروژه‌اند، نه از آموزش‌های عمومی.

---

## بخش ۱ — CMS هدلس یعنی چه

### وردپرس سنتی

وردپرس هم محتوا را نگه می‌دارد، هم HTML را می‌سازد. یک درخواست می‌آید، PHP اجرا می‌شود، قالب رندر می‌شود، HTML برمی‌گردد.

ساده است. ولی سه محدودیت دارد:

**سرعت** — هر بازدید یعنی اجرای PHP و کوئری دیتابیس.
**انعطاف** — رابط کاربری به قالب گره خورده.
**امنیت** — همان چیزی که محتوا را نگه می‌دارد، در معرض اینترنت است.

### هدلس

محتوا و نمایش از هم جدا می‌شوند:

```
وردپرس  ──GraphQL──▶  Next.js  ──HTML──▶  خواننده
(محتوا)                (نمایش)
```

وردپرس فقط یک **API** است. کسی صفحه‌اش را نمی‌بیند. Next.js محتوا را می‌خواند و صفحه می‌سازد.

در این پروژه:

```
wp.thefinance.ir/mag/graphql   ← اندپوینت
thefinance.ir/mag              ← آنچه خواننده می‌بیند
```

### قیمتی که می‌دهی

هدلس رایگان نیست. سه چیز که در وردپرس سنتی خودکار بودند، حالا باید ساخته شوند:

**پیش‌نمایش** — وردپرس دیگر نمی‌داند صفحه چطور رندر می‌شود. باید یک روت جدا بسازی که با یک سکرت احراز هویت کند.

**ریدایرکت‌ها** — افزونه‌ی ریدایرکت وردپرس روی سایت اثری ندارد. باید قوانین را از CMS بخوانی و در Next اعمال کنی.

**و آدرس‌ها** — این بزرگ‌ترینش است و در بخش ۶ توضیحش می‌دهم.

## بخش ۲ — چهار روش رندر در Next.js

مهم‌ترین مفهومی که باید بفهمی. Next چهار حالت دارد و انتخاب اشتباه یا سایت را کند می‌کند یا از گوگل پنهان.

### SSG — ساخت در زمان بیلد

صفحه یک بار موقع بیلد ساخته می‌شود و به‌صورت فایل استاتیک سرو می‌شود.

**سریع‌ترین.** ولی برای به‌روزرسانی باید دوباره بیلد بگیری.

### SSR — ساخت در هر درخواست

هر بار که کسی صفحه را می‌خواهد، سرور آن را می‌سازد.

**همیشه تازه.** ولی هر بازدید یعنی کار سرور.

### CSR — ساخت در مرورگر

سرور یک صفحه‌ی خالی می‌فرستد، جاوااسکریپت داده را می‌گیرد و صفحه را می‌سازد.

**برای سئو فاجعه است.** خزنده‌ی گوگل صفحه‌ی خالی می‌بیند.

در این پروژه یک بار همین اتفاق افتاد: یک خط `if (!mounted) return null` در یک provider ریشه‌ای باعث شد **کل سایت** برای خزنده خالی باشد. ماه‌ها کار سئو بی‌اثر بود و هیچ‌کس نفهمید، چون در مرورگر همه‌چیز درست دیده می‌شد.

### ISR — ساخت استاتیک با تازه‌سازی خودکار

بهترین هر دو. صفحه استاتیک است، ولی هر N ثانیه یک بار در پس‌زمینه دوباره ساخته می‌شود.

در این پروژه:

```ts
// src/app/[slug]/page.tsx
export const revalidate = 300;
```

یعنی هر پنج دقیقه. خواننده همیشه نسخه‌ی استاتیک و سریع می‌گیرد؛ اگر آن نسخه بیش از پنج دقیقه عمر داشته باشد، Next در پس‌زمینه تازه‌اش می‌کند.

**نتیجه:** مقاله‌ی جدید حداکثر پنج دقیقه بعد از انتشار روی سایت است، بدون هیچ بیلدی.

### یک تله که در همین پروژه گرفتیم

```ts
export const revalidate = 300;   // ← بی‌اثر بود
```

یک روت پویا **بدون** `generateStaticParams` کاملاً داینامیک در نظر گرفته می‌شود. `revalidate` نادیده گرفته می‌شود و هر درخواست از نو رندر می‌شود.

فیکسش:

```ts
export async function generateStaticParams() {
  const slugs = await getAllSlugs();
  return slugs.map((slug) => ({ slug }));
}
```

با این، Next می‌داند چه صفحاتی وجود دارند، آنها را در بیلد می‌سازد، و `revalidate` معنا پیدا می‌کند.

**درس عمومی:** در Next، تنظیمات به‌صورت ساکت نادیده گرفته می‌شوند اگر پیش‌شرطشان فراهم نباشد. هیچ خطایی نمی‌گیری. باید خروجی واقعی را چک کنی.

## بخش ۳ — Server Components و Client Components

در App Router، هر کامپوننت **پیش‌فرض روی سرور** اجرا می‌شود.

```tsx
// این روی سرور اجرا می‌شود — بدون 'use client'
export default async function ArticlePage({ params }) {
  const article = await getArticle(params.slug);
  return <article>{article.title}</article>;
}
```

می‌تواند `async` باشد، مستقیم از API بخواند، و کدش هرگز به مرورگر نمی‌رود.

برای تعامل، `'use client'` لازم است:

```tsx
'use client';
import { useState } from 'react';

export function ThemeToggle() {
  const [theme, setTheme] = useState('dark');
  // ...
}
```

### تله‌ای که در این پروژه خوردیم

یک سرور کامپوننت که مقداری را از ماژول `'use client'` وارد می‌کند، **مقدار واقعی را نمی‌گیرد** — یک client reference proxy می‌گیرد که همیشه truthy است.

```tsx
// در NewsletterCta.tsx که 'use client' دارد
export const NEWSLETTER_ENABLED = false;

// در یک سرور کامپوننت
import { NEWSLETTER_ENABLED } from './NewsletterCta';
if (NEWSLETTER_ENABLED) { ... }   // ← همیشه true
```

بیلد تمیز بود، خطایی نبود، و فقط `curl` روی HTML سرو‌شده نشانش داد.

**قاعده:** فلگ‌ها و ثابت‌های پیکربندی در ماژول‌های خنثی زندگی می‌کنند، نه در کامپوننت‌های کلاینت.

## بخش ۴ — لایه‌بندی داده

ساختار پروژه:

```
src/features/mag/
  api/v1/
    mag.api.ts       ← API واقعی (GraphQL)
    mag.mock.ts      ← نسخه‌ی ماک
    mag.service.ts   ← انتخاب‌کننده
  components/
  lib/
  types/
```

### چرا `mag.service.ts` وجود دارد

هیچ کامپوننتی مستقیم از `mag.api.ts` نمی‌خواند. همه از `mag.service.ts` می‌خوانند، و آن تصمیم می‌گیرد کدام منبع:

```ts
const USE_MOCK = process.env.NEXT_PUBLIC_USE_MOCK === 'true';
const source = USE_MOCK ? mock : real;

export const getArticle = (slug) => source.getArticle(slug);
```

**فایده:** توسعه بدون CMS، تست بدون شبکه، و تعویض منبع یک تغییر env است نه refactor.

### و یک ترفند تایپی که ارزش یادگیری دارد

```ts
type MagSource = {
  getArticle: typeof mock.getArticle;
  getMarkets: typeof mock.getMarkets;
  // ...
};

const mockSource: MagSource = mock;
const realSource: MagSource = real;
```

این تضمین می‌کند ماک و API واقعی **دقیقاً یک قرارداد** دارند. اگر امضای یکی عوض شود، بیلد می‌شکند — نه اینکه در زمان اجرا مقدار غلط برگردد.

بدون این، ماک به‌مرور از واقعیت فاصله می‌گیرد و کسی نمی‌فهمد.

## بخش ۵ — توکن‌های طراحی

هیچ کامپوننتی رنگ نمی‌نویسد. همه به **نقش** ارجاع می‌دهند:

```css
:root, [data-theme='v1'] {
  --surface: #040c1f;
  --surface-raised: #071331;
  --text-primary: #ffffff;
  --text-secondary: rgba(255, 255, 255, 0.70);
  --text-muted: rgba(255, 255, 255, 0.50);
}
```

و کامپوننت:

```tsx
<div className="bg-[var(--surface-raised)] text-[var(--text-secondary)]">
```

### چرا این مهم است

سه تم داریم: `v1` (navy تیره)، `v2-dark`، `v2-light`. اگر کامپوننت رنگ بنویسد، هر تم جدید یعنی ویرایش هر کامپوننت.

با توکن، **یک فایل عوض می‌شود**.

### و درسی که با اندازه‌گیری گرفتیم

در همین پروژه، دیزاین یک رنگ برای خطوط پیشنهاد داد که ۱.۹۱:۱ اندازه شد — زیر کف ۳:۱ که WCAG برای کنترلی که مرزش تنها نشانه‌اش است می‌خواهد.

راه‌حل: آن رنگ به‌عنوان خط تزئینی ماند، و برای هر چیز تعاملی یک توکن جدا ساخته شد که ۳.۹۵ اندازه می‌شود.

**درس:** «به‌نظر می‌رسد کافی است» جای اندازه‌گیری را نمی‌گیرد. و یک اسکریپت که توکن‌ها را می‌خواند و نسبت‌ها را حساب می‌کند، از هر بازبینی چشمی قابل‌اتکاتر است.

## بخش ۶ — `basePath` و چرا همه‌چیز را سخت می‌کند

مجله زیر `/mag` زندگی می‌کند:

```ts
// next.config.ts
basePath: '/mag',
```

Next خودکار همه‌ی لینک‌ها و دارایی‌ها را با این پیشوند می‌سازد. `/archive` می‌شود `/mag/archive`.

### ولی وردپرس این را نمی‌داند

`siteurl` وردپرس روی `thefinance.ir/mag` است، پس آدرس‌هایی می‌سازد که به مسیر Next اشاره می‌کنند — و آنجا وردپرسی نیست.

نتیجه: پنل ادمین، دارایی‌هایش، آپلود رسانه، همه ۴۰۴.

راه‌حل سیزده فیلتر PHP شد که آدرس‌ها را بازنویسی می‌کنند. جزئیاتش در سند مرجع است، ولی **درس معماری** این است:

> وقتی دو سیستم درباره‌ی «آدرس این چیست» اختلاف دارند، هر لایه‌ای که بینشان است باید ترجمه کند — و هر ترجمه‌ای که از قلم بیفتد، یک ۴۰۴ ساکت است.

### و یک چیز که هیچ فیلتر PHP نمی‌گیرد

```js
wp.ajax.settings.url  // '/mag/wp-admin/admin-ajax.php'
```

یک مسیر **نسبی**. هیچ فیلتری نمی‌تواند مچش کند چون هاستی برای بازنویسی وجود ندارد.

راه‌حل در دو لایه: یک اسکریپت inline در وردپرس، و یک `rewrite` در nginx برای هر چیزی که از قلم بیفتد.

## بخش ۷ — ریدایرکت‌ها و چرا حیاتی‌اند

۸۹٪ کلیک‌های ارگانیک مجله روی آدرس‌های قدیمی می‌نشیند که فقط با ۳۰۱ حل می‌شوند.

اگر بدون نگاشت ریدایرکت مهاجرت می‌کردیم، بیشتر ترافیک بخش از دست می‌رفت.

### معماری

قوانین در وردپرس نگه داشته می‌شوند (تیم سئو آنجا اضافه می‌کند)، از طریق GraphQL خوانده می‌شوند، و در Next به یک جدول کامپایل می‌شوند:

```
wp mu-plugin  →  magRedirects (GraphQL)  →  redirect-source.ts  →  redirects.ts
```

و `/mag/health` گزارش می‌دهد که منبع در دسترس است و چند قانون کامپایل شده:

```json
"redirectSource": {
  "reachable": true,
  "count": 19,
  "compiledCount": 19,
  "missingKnown": [],
  "missingCompiled": []
}
```

**چرا این الگو خوب است:** تیم سئو بدون دخالت مهندس قانون اضافه می‌کند، و اگر ارتباط قطع شود، `health` فوراً می‌گوید.

### و یک باگ سئو که پیدا کردیم

`?page=2` و `?page=3` و `?page=99` همه **صفحه‌ی یک** را با ۲۰۰ برمی‌گرداندند.

Next کوئری ناشناخته را نادیده می‌گیرد. نتیجه: محتوای تکراری روی بی‌نهایت URL — بدتر از ۴۰۴، چون گوگل ایندکسشان می‌کند.

راه‌حل: ۳۰۱ به مسیر کانونیکال.

```
/mag/archive?page=3  →  301  →  /mag/archive/page/3
```

**چرا مسیر و نه کوئری:** کوئری‌استرینگ روت را داینامیک می‌کند، پس prerender نمی‌شود و در سایت‌مپ نمی‌آید.

## بخش ۸ — RTL و چیزهایی که فقط در فارسی پیش می‌آیند

### از خصوصیات منطقی استفاده کن

```css
/* بد */
margin-left: 1rem;

/* خوب */
margin-inline-start: 1rem;
```

`inline-start` در RTL راست است و در LTR چپ. با آن، یک استایل‌شیت هر دو جهت را می‌گیرد.

### جاستیفای — و درسی درباره‌ی قاعده‌های اندازه‌گیری‌نشده

قاعده‌ی اولیه‌ی این پروژه این بود: **هرگز جاستیفای نکن.** دلیلش این بود که فارسی بدون کشیده «رودخانه‌های سفید» می‌سازد — فاصله‌های نامنظم بین کلمات که خواندن را سخت می‌کنند.

مکانیزم درست بود. **ولی هیچ‌وقت اندازه‌گیری نشده بود.**

وقتی اندازه گرفتیم — حدود ۴۲۰ فاصله‌ی بین‌کلمه‌ای در یک مقاله‌ی ۲۴ عنوانی:

| عرض | تراز | میانه | بدترین | نسبت به فاصله‌ی معمولی |
|---|---|---|---|---|
| ۱۴۴۰ | راست‌چین | ۴.۵۰ | ۴.۵۰ | ۱.۰۰× |
| ۱۴۴۰ | جاستیفای | ۵.۲۸ | ۷.۲۷ | **۱.۶۲×** |
| ۳۹۰ | راست‌چین | ۴.۲۵ | ۴.۲۵ | ۱.۰۰× |
| ۳۹۰ | جاستیفای | ۶.۸۹ | ۱۲.۱۴ | **۲.۸۶×** |

نتیجه: **این قاعده‌ای درباره‌ی عرض ستون است، نه درباره‌ی فارسی.**

در ستون ۷۰۰ پیکسلی، خط آن‌قدر پهن است که فرصت شکست کافی پیدا می‌کند. بدترین فاصله ۱.۶۲ برابر است و هیچ فاصله‌ای به دو برابر میانه نمی‌رسد — رودخانه‌ای نمی‌ماند.

در ۳۵۰ پیکسل، میانه از اول ۶۲٪ پهن‌تر از طبیعی است و بدترین نزدیک به سه برابر. **آنجا قاعده درست است.**

پس: **جاستیفای در ۷۶۸ و بالاتر، راست‌چین زیر آن.**

### و تستی که از همه مهم‌تر بود

نیم‌فاصله (ZWNJ) در کلماتی مثل «می‌پردازیم». اگر مرورگر آن را نقطه‌ی توزیع فاصله می‌دید، **کلمات از وسط باز می‌شدند** — که در هیچ عرضی قابل شیپ کردن نیست.

اندازه‌گیری: ۷۲.۰۵ پیکسل، با جاستیفای و بدون آن یکسان. مصون است.

و برای اینکه به رفتار پیش‌فرض تکیه نشود:

```css
text-justify: inter-word;
```

### درس عمومی

**قاعده‌ای که اندازه‌گیری نشده، یک فرضیه است.**

این قاعده در مستندات پروژه نوشته شده بود، در چند سند تکرار شده بود، و من هم آن را به‌عنوان واقعیت گفتم. تا وقتی کسی اندازه گرفت و دید که در نصف موارد اشتباه است.

قاعده‌های خوب عدد دارند. اگر قاعده‌ای فقط «هرگز» می‌گوید بدون اینکه بگوید در چه شرایطی و با چه اندازه‌ای، ارزشش را باید دوباره سنجید.

### عدد یا شناسه؟

```ts
// بد — سال را ۱٬۴۰۵ می‌کند
new Intl.NumberFormat('fa-IR').format(year);
```

`Intl.NumberFormat` جداکننده‌ی هزارگان می‌گذارد. برای مبلغ درست است، برای سال و شماره‌ی صفحه فاجعه.

**قاعده:** قبل از فرمت کردن، بپرس این عدد **کمیت** است یا **شناسه**.

### متن دوجهته

```
تحلیل فاندامنتال (Fundamental Analysis) چیست؟
```

الگوریتم دوجهته‌ی یونیکد گاهی پرانتز را در جای غلط می‌گذارد. راه‌حل، ایزوله کردن رشته‌ی لاتین است:

```tsx
<bdi>{latinRun}</bdi>
```

### و `<cite>` که همیشه ایتالیک است

هر مرورگری `<cite>` را ایتالیک می‌کند. قانون `blockquote { font-style: normal }` فقط با **وراثت** به آن می‌رسد، ولی قانون مرورگر روی خود عنصر است و برنده می‌شود.

نتیجه: هر نقل‌قول فارسی با کج‌شدگی مصنوعی رندر می‌شد — چیزی که فونت فارسی برایش طراحی نشده.

## بخش ۹ — تصاویر و مسئله‌ی hairpin

### `next/image` چه می‌کند

تصویر را در اندازه‌های مختلف بهینه می‌کند، به WebP تبدیل می‌کند، و lazy load می‌گذارد.

ولی بهینه‌ساز **سمت سرور** تصویر را fetch می‌کند — از داخل کانتینر.

### مشکلی که خوردیم

آدرس تصاویر `https://thefinance.ir/mag/...` بود. بهینه‌ساز از داخل کانتینر آن را می‌خواست، درخواست از سرور بیرون می‌رفت، به CDN می‌رسید، و برمی‌گشت به همان سرور — **hairpin** — و تایم‌اوت می‌شد.

همه‌ی تصاویر ۵۰۲.

### راه‌حل و ظرافتش

دو آدرس لازم است:

```ts
// آنچه در JSON-LD و og:image می‌رود — عمومی
url: toPublicUrl(image.sourceUrl)

// آنچه بهینه‌ساز fetch می‌کند — هاست CMS
imageSrc(url)  // در نقطه‌ی استفاده
```

اگر فقط یکی را عوض می‌کردیم، یا تصاویر می‌شکستند یا داده‌ی ساختاریافته به هاست `noindex` اشاره می‌کرد.

**درس:** یک مقدار می‌تواند دو مصرف‌کننده با نیازهای متفاوت داشته باشد. آن را در نقطه‌ی مصرف تبدیل کن، نه در منبع.

## بخش ۱۰ — محتوای خام از CMS

بدنه‌ی مقاله HTML خام از وردپرس است. یعنی هر چیزی ممکن است داخلش باشد.

در این پروژه چهار چیز پیدا شد که دیزاین انتظارشان را نداشت:

**`<iframe width="560">`** — بدون قانونی در استایل‌شیت، ۶۰۰ پیکسل سرریز افقی می‌ساخت.

**`<div style="width:900px">`** از ویرایشگر کلاسیک.

**فهرست مطالب تزریقی** از یک افزونه — هر مقاله دو فهرست داشت.

**و تصاویر eager و بدون اندازه** — مقاله‌ای با ده تصویر، یازده درخواست مسدودکننده علیه LCP می‌فرستاد.

### الگوی حل

یک لایه‌ی `sanitize` که HTML را قبل از رندر پردازش می‌کند:

- محتوای پهن در ظرف `overflow-x: auto` خودش می‌رود
- عرض‌های اینلاین حذف می‌شوند
- تصاویر `loading="lazy"` و اندازه می‌گیرند
- فهرست تزریقی حذف می‌شود

و یک **invariant** که این را دائمی می‌کند:

```bash
npm run check:invariants
```

اسکریپتی که علیه بدنه‌ی واقعی مقالات در چند عرض اجرا می‌شود و اگر چیزی سرریز کند، اسم عنصر مقصر را می‌گوید.

**درس مهم:** اولین نسخه‌ی این چک علیه **فیکسچر** اجرا می‌شد و تمیز گزارش می‌داد. فیکسچرها را همان کسی نوشته بود که کد را نوشته، پس فقط تأیید می‌کردند که کد با انتظار خودش می‌خواند.

> چکی که فقط حالت‌های خوش‌فرم را می‌بیند، همیشه پاس می‌شود.

## بخش ۱۱ — سئو در عمل

### سه چیزی که هر صفحه لازم دارد

**عنوان و توضیحات یکتا** — از CMS، نه تولیدشده.

**canonical** — می‌گوید آدرس اصلی این محتوا کدام است. بدون آن، همان مقاله روی دو هاست محتوای تکراری می‌شود.

**داده‌ی ساختاریافته** — `NewsArticle` برای خبر، `Article` برای محتوای ماندگار.

### YMYL

محتوای مالی زیر «Your Money or Your Life» است. گوگل استانداردهای سخت‌گیرانه‌تری اعمال می‌کند و **سیگنال‌های اعتبار نویسنده** لازم است: نام، بیوگرافی، و اتصال به داده‌ی ساختاریافته.

### و درسی که گران بود

سئو فقط وقتی کار می‌کند که محتوا **سمت سرور** رندر شود. آن `if (!mounted) return null` که گفتم، ماه‌ها کار سئو را بی‌اثر کرده بود.

**همیشه چک کن:**

```bash
curl -s https://thefinance.ir/mag/ | grep -c "<article"
```

اگر صفر باشد، خزنده هم صفر می‌بیند.

## بخش ۱۲ — الگوهایی که ارزش برداشتن دارند

جدا از این پروژه، اینها در هر پروژه‌ای کار می‌کنند:

**اندپوینت health که واقعیت را می‌گوید** — نه فقط «زنده‌ام»، بلکه کدام بیلد، کدام منبع داده، چند ریدایرکت، و آیا چیزی از قلم افتاده.

**یک نقطه‌ی تعویض منبع داده** — همه از یک فایل می‌خوانند، آن فایل تصمیم می‌گیرد.

**قرارداد تایپی بین ماک و واقعی** — تا ماک از واقعیت فاصله نگیرد.

**توکن‌های دو لایه** — نقش‌های معنایی، نه رنگ‌ها.

**invariant که علیه داده‌ی واقعی اجرا می‌شود** — نه فیکسچر.

**و کامنتی که دلیل را می‌گوید، نه کار را:**

```ts
// بد
// آدرس را به هاست CMS تبدیل می‌کند

// خوب
// The image optimizer fetches server-side from inside the container; nginx on
// the frontend listens on :80 only — TLS terminates at the CDN — so a fetch of
// https://thefinance.ir/... leaves the box, hits the CDN and hairpins back,
// which times out and every image 502s.
```

کد چه کاری می‌کند از خودش پیداست. **چرا** فقط در کامنت زنده است — و آن چیزی است که شش ماه بعد کسی را از تکرار همان اشتباه نجات می‌دهد.
